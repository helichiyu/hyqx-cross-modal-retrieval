你问到关键了。我逐个答：

## ① 记的是"数据集"还是"样本"

**是样本**——数据集里的具体条目（ITM 号），不是数据集本身。

## ② 不同模态记什么

| 搜到什么 | 记什么 | 不记什么 |
| --- | --- | --- |
| 文档 | 文档名 + ID | 正文 |
| 图片 | 图片名 + ID | 图片本体、缩略图 |
| 视频 | **视频名 + ID** | **帧、时长内容** |
| 音频 | 音频名 + ID | 音频流 |

**视频只记"这条视频叫什么"，不记它的任何帧。**

## ③ 会不会爆炸——算给你看

| 方案 | 单次 | 1万次/天 | 30 天 |
| --- | --- | --- | --- |
| 全量快照（含图片路径） | ~6 MB | 60 GB | ❌ 爆 |
| **Top-20（ID + 名称 + 分数）** | 1.2 KB | 12 MB | 360 MB |
| **Top-20（只存 ID + 分数）** | **0.3 KB** | **3 MB** | **90 MB** ✅ |

**「ID + 名称」确实会持续长**（一年 4 GB），但**只存 ID** 就压到 90 MB/30 天，完全可控。

## ④ 我的建议：只存 ID，名称实时回查

```text
存的：{ 任务号, 搜索词, 时间, 结果数, 赞踩数, Top-20: [ITM001/0.94, ITM005/0.92, ...] }
                ↑ 只有 ID + 分数，没有名称
```

**详情页打开时**：

- 拿 ID 去库里查名称 → 还在就显示名字；
- 条目被删了 → 显示「已删除」；
- 这样**名称不占存储**，但看的时候一样能看。

## ⑤ 再加两条兜底

| 措施 | 效果 |
| --- | --- |
| **30 天滚动删除** | 只留近期，有上界 |
| **被踩/被标记的条目永久保留** | 治理要追溯，这几条很小（每次 0~5 条） |

## 一句话

> **存"样本 ID + 分数"（0.3 KB/次），不存名称和内容；详情页实时回查名称。30 天过期，被踩的永久留。**

这样：

- 存储有上界（90 MB/30 天）；
- 还能判断"大海搜出来的是不是海"（看名称）；
- 治理有依据（被踩条目留底）。
